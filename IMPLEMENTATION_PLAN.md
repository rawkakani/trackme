# SD MVP — Implementation Plan

An agent builds the MVP from this file. Read in this order: `README.md` (why), `FOUNDATION.md` (what was
asked), this file (how), and `openapi.yaml` (the contract). If this file and `openapi.yaml` disagree, `openapi.yaml`
wins. Fix this file to match it.

## 0. What the MVP has to do

One flow, end to end:

1. An integrator calls `POST /v1/orders` with the customer (email + phone), address, technician (email or phone)
   and appointment.
2. SD puts the order in that technician's queue for the day and returns the **order id** with the customer's
   private tracking link (and the technician's link the first time that technician appears). SD sends no email
   or SMS: the integrator passes the links on through its own channels.
3. The customer opens the link and sees their place (`3rd of 7`, `2 ahead of you`), the most likely arrival
   time, and whether the booking is an exact time or an arrival window.
4. The technician opens their link and sees the day's tasks in order. They tap a task to see the person,
   the address, directions and contact details, then tap through **Start → Arrived → Done** (or
   **Can't complete**, with a reason).
5. When the technician taps **Start** on an order, that customer sees it is their turn, with distance and a
   live ETA. Everyone behind them sees their queue and ETA move. No refresh needed.

Every change is written to an append-only event log (README: accountability). A change of plan shows on the
customer's tracking page the moment it happens, with the reason (README: guiding principle).

**Not in the MVP** (stored where the payload has the fields, but no views or sends): **email and SMS sending of
any kind**, **"bump yourself up" (pay to move to the front) and payments of any kind** (SD manages orders
only; payment is handled outside it), manager view and notifications, provider/ISP view and notifications, creating orders from chat, voice
notes, chat parsing, outgoing webhooks, multi-tenant organisations.

## 3. Domain model

### 3.1 Entities (SQLite tables)

```
api_keys        id, name, key_hash, prefix, support_phone, support_email, created_at, revoked_at
customers       id cus_*, email UNIQUE NULL, phone UNIQUE NULL, name, created_at
technicians     id tec_*, email UNIQUE NULL, phone UNIQUE NULL, name, token_hash UNIQUE, created_at
orders          id ord_*, api_key_id, external_ref, customer_id, technician_id,
                address_json, lat, lng,
                appt_date (YYYY-MM-DD), appt_kind, appt_start, appt_end,
                duration_min, service, notes,
                manager_json NULL, provider_json NULL,
                status, rank INTEGER,
                tracking_token, tracking_token_hash UNIQUE, message NULL,
                created_at, updated_at,
                UNIQUE(api_key_id, external_ref)
order_events    id evt_*, order_id, type, actor, data_json, at          -- append-only, never updated
technician_pos  technician_id PK, lat, lng, accuracy_m, at              -- latest only
idempotency     api_key_id, key, request_hash, response_json, created_at, PK(api_key_id, key)
```

Indexes: `orders(technician_id, appt_date, rank)`, `orders(customer_id)`, `order_events(order_id, at)`.

### 3.2 Identity rules

- Emails lowercased and trimmed. Phones normalised to E.164 with a default country of `ZA` (configurable).
- **Customer** upsert: match by email first, then phone. If the email matches one customer and the phone
  matches another, the email wins and the phone is not moved (log a `system` event). Fill in missing
  name/phone/email on the existing record. Never overwrite a non-empty field from an order.
- **Technician** upsert: the same rules (email, then phone).
- **Manager / provider**: stored as JSON on the order only. No tables until they get views.

### 3.3 Order status (State pattern)

```
scheduled ──start──▶ en_route ──arrive──▶ on_site ──complete──▶ completed
    │                    │                    │
    │cancel              └────unable──────────┴──▶ unable
    ▼
cancelled
```

`packages/domain/order.ts` exports a transition table `{ [status]: { [action]: nextStatus } }` and one function
`transition(order, action): Order | DomainError`. Every service goes through it. No `if (status === ...)`
anywhere else.

Rules:
- `start` only when the technician has no other order `en_route`/`on_site` (one active order at a time).
- `start` is allowed on any `scheduled` order, not only the first. When a technician starts an order out of
  turn, it moves to the front of the remaining queue (the queue shows what is really happening).
- `unable` needs a note. The note becomes the customer's `message`.
- `scheduled` orders can be rescheduled or reassigned (PATCH). Others return 409.

### 3.4 The day queue

A queue is all orders for one `(technician_id, appt_date)` except `cancelled`. Each order has an integer `rank`.

- **Order of the list:** finished orders (`completed`, `unable`) by when they finished, then the active order,
  then `scheduled` orders by `rank`.
- **New order:** `rank` is chosen by the `QueueOrdering` strategy. The MVP strategy, `ByAppointment`, places it by
  `appt_start` (exact times and window starts both count), then by `created_at`, among scheduled orders.
- **Ranks** are rewritten for the whole day queue in one transaction whenever the order changes (days are small;
  no fractional ranks).
- **position** = 1-based index in the list above. **total** = list length. **ahead** = orders before it that are
  `scheduled`, `en_route` or `on_site`.

`DayQueue` is a pure class built from rows: `DayQueue.from(orders)`, `.insert(order, strategy)`,
`.moveToFront(id)`, `.remove(id)`, `.place(id) → {position,total,ahead}`, `.ranks() → Map<id, rank>`. Repositories
load rows, the domain decides, repositories save ranks. Every queue change emits `order.queue_moved` for each
order whose position changed, so each affected customer gets one live update.

### 3.5 ETA (Strategy)

```ts
interface EtaEstimator { estimate(ctx: EtaContext): Eta | null }
```

Three implementations, picked by a small `EtaPolicy` from the order's state:

| Basis | When | How |
|---|---|---|
| `schedule` | technician has not started the day (no order active or finished today) | `exact` → `appt_start`. `window` → walk the queue from the window start (or the day start, `SD_DAY_START`, default 08:00) adding `duration + travel` for each order ahead. Clamp to the window. |
| `queue` | day started, this order is `scheduled` | now (or the active order's expected finish) + Σ(duration + travel) for orders ahead. |
| `live` | this order is `en_route` and a position from the last 5 minutes is known | haversine distance ÷ `SD_AVG_SPEED_KMH` (default 30) × `SD_ROAD_FACTOR` (default 1.4). |

Travel between stops: haversine between the two addresses × road factor ÷ average speed when both have
coordinates, else `SD_DEFAULT_TRAVEL_MIN` (default 25). `earliest`/`latest` = ±20% of the remaining time,
rounded to 5 minutes. All constants are config, not code. A routing API (real road time) can be a fourth
estimator later without touching callers.

The customer page shows `basis` honestly ("Based on the technician's live location, 2 min ago" vs "Estimate from
the schedule").

## 4. Design patterns (where each one lives, and why)

Use a pattern only where it removes a branch or an import. Do not add classes for symmetry.

| Pattern | Where | What it buys |
|---|---|---|
| **Facade** | `OrderService`, `TrackingService`, `TechnicianService` | Route handlers call one method. Transactions and events are hidden behind it. |
| **Repository** | `apps/api/src/db/repositories/*` behind interfaces in `packages/domain` | The domain never sees SQL. Tests use in-memory SQLite with the same code. |
| **State** | `order.ts` transition table | One place decides what each status allows; `allowedActions` for the UI comes from it. |
| **Strategy** | `QueueOrdering`, `EtaEstimator` | Ordering and ETA rules change without touching services. |
| **Command** | `commands/` — `StartTask`, `ArriveTask`, `CompleteTask`, `UnableTask` keyed by action type in one table | `POST .../actions` is one lookup, not a switch. Each command validates, transitions, saves, emits. |
| **Observer** | `realtime/event-bus.ts`: services publish `DomainEvent`s after commit; subscribers are the event log writer and the SSE hub | Adding a reaction later (email/SMS, outgoing webhooks, manager notifications) = one subscriber, no service change. |

The composition root (`main.ts`) is the only place that knows concrete classes. Everything else takes
interfaces through constructor parameters.

### 4.1 Events → reactions

| Event | Event log | SSE (customer) | SSE (technician) | Tracking page `message` |
|---|---|---|---|---|
| `order.created` | ✓ | | ✓ | |
| `order.rescheduled` / `order.reassigned` | ✓ | ✓ | ✓ (old and new technician) | new date/time + reason |
| `order.cancelled` | ✓ | ✓ | ✓ | reason |
| `order.queue_moved` | ✓ | ✓ | ✓ | |
| `order.status_changed` → `en_route` | ✓ | ✓ | ✓ | |
| `order.status_changed` → `unable` | ✓ | ✓ | ✓ | the technician's note |
| `order.status_changed` → `completed` | ✓ | ✓ | ✓ | |
| location ping | not logged | ✓ (your-turn customer only, throttled to 1 per 15 s) | | |

Subscribers run after the database commit, never inside it. No email or SMS is sent for any event. When sending
is added later, it is one more subscriber on this bus.

### 4.2 Create order response

`POST /v1/orders` returns `201` with only what the integrator needs to pass on:

```json
{
  "orderId": "ord_8f2kd93ka0s9d8f7",
  "externalRef": "ISP-88213",
  "status": "scheduled",
  "queue": { "position": 3, "total": 3, "ahead": 2 },
  "trackingUrl": "https://sd.example/t/…",
  "technicianUrl": "https://sd.example/tech/…"
}
```

`technicianUrl` is there only when this order created the technician's link. Technician tokens are stored hashed,
so that link cannot be shown again; a lost one is replaced with `bun run tech:rotate`. The tracking token is
stored as-is (it only opens the customer's own status, never an address or phone), so `GET /v1/orders/{orderId}`
always returns the full order with its `trackingUrl`.

## 5. Security

- **API keys**: `sd_live_` + 32 random bytes base62. Stored as SHA-256. Shown once by `bun run key:create <name>`.
- **Tracking and technician tokens**: 32 random bytes base64url, looked up by their SHA-256 hash. The technician
  token is stored only as the hash. The tracking token is also kept as-is so the integrator can fetch the link
  again (see 4.2). Links: `${SD_PUBLIC_URL}/t/<token>` and `${SD_PUBLIC_URL}/tech/<token>`. A technician token can
  be rotated with `bun run tech:rotate <email|phone>`, which prints the new link.
- The tracking response is built by a single mapper `toTrackingView(order, queue, eta, pos)`. It takes only what
  it outputs, so nothing about other customers can leak. Test it with a fixture that has other customers' data in
  the same queue and assert none of it appears.
- Technician endpoints check the order belongs to the token's technician (404 otherwise, not 403).
- Rate limits (in memory, per IP): 60/min on `/v1/track/*`, 120/min on `/v1/tech/*`, 600/min per API key.
- `Referrer-Policy: no-referrer` on the web app so tokens never leak to the maps app.
- No PII in logs: log ids, never emails, phones or addresses.

## 6. API implementation notes

The contract is `openapi.yaml`. Notes the YAML cannot say:

- `routes.ts` is a table: `{ "POST /v1/orders": h(createOrder, { auth: "apiKey", body: CreateOrderSchema }) }`.
  One `h()` wrapper does auth, zod parsing, calling the service, mapping `DomainError` to problem+json, and
  JSON output. Handlers are 3–5 lines.
- `Idempotency-Key`: hash the canonical JSON body. Same key + same hash → return the stored response with the
  stored status. Same key + different hash → 409. Keep 24 hours.
- `GET /v1/orders` paginates with an opaque cursor (`base64url(created_at|id)`).
- Serve `openapi.yaml` at `/v1/openapi.yaml` so integrators can read it.
- SSE: `realtime/sse.ts` keeps `Map<topic, Set<controller>>`. Topics are `order:<id>` and
  `tech:<technicianId>:<date>`. On connect, send the current view at once, then each change. Heartbeat comment
  every 25 s. Remove the controller on abort.

## 7. Web app (Wirekyt + UI SDK)

### 7.1 Setup

1. Vite React TS app in `apps/web`, Tailwind v4 via `@tailwindcss/vite`.
2. Follow https://ui.wirekyt.com/react/installation with **bun**:
   `bun add @fontsource-variable/inter @wirekyt/dom @wirekyt/react class-variance-authority cn lucide-react shadcn tw-animate-css`.
   Copy its `components.json` (registry `https://ui.wirekyt.com/react/r/plain/{name}.json`, style `plain`),
   the tsconfig `@/*` alias and the `src/index.css` block from the page.
3. Add components with `bunx shadcn@latest add <name>` from that registry. Known gotchas from an earlier
   Wirekyt project: `item` and `toast` fail through the CLI (bare `registryDependencies`), so copy them from the
   registry JSON by hand. "plain" components use tokens the base CSS lacks (`fill-*`, `control*`, `field*`,
   `primary-border*`, `shadow-*-control`). Define them at the end of `index.css`.
4. `bun add @ui-sdk/react @ui-sdk/core` and `bunx skills add vercel-labs/ui --skill ui-sdk` so the agent has the
   UI SDK skill. Use UI SDK only for **Meter** (queue position), **Timeline** (order progress) and
   **SegmentedControl** if needed. Style them with the same Tailwind tokens as Wirekyt. Do not import
   `@ui-sdk/core/web.css`: one token system (Wirekyt's) on the page.
5. TanStack Router with the Vite plugin (file routes), TanStack Query for data. `lib/live.ts` exposes
   `useLive(queryKey, streamUrl)`: opens an `EventSource` and writes each message into the Query cache with
   `setQueryData`. It reconnects with backoff and falls back to a 30 s `refetchInterval` while disconnected.

Wirekyt components to add: `button`, `badge`, `item`, `empty`, `skeleton`, `separator`, `sheet`, `dialog`,
`alert`, `textarea`, `spinner`, `toast`, `kbd` (none needed beyond these).

### 7.2 Look: minimal, borderless, bold

Set once in `index.css` tokens. Never per component:

- **Borderless**: `--border` and `--input` set to `transparent`. Separation comes from spacing and one muted
  surface (`--muted`) for grouped areas, never from lines. `separator` only between list rows, at muted
  strength.
- **Bold**: Inter Variable. The big number on each screen (queue position, ETA) is `text-7xl font-black
  tracking-tight`. Headings `font-bold`. Body `font-medium`. Two text colours only: foreground and muted.
- One accent colour for the single primary action per screen (`--primary`). Status uses a small dot + word,
  never a coloured card.
- No shadows except on overlays (`sheet`, `dialog`). Radius from the Wirekyt token.
- Mobile first: both audiences are on phones. Max content width 28rem, centred. Thumb-reach primary action fixed
  at the bottom.
- Light and dark from the Wirekyt token set (`.dark`, follow the system).

### 7.3 Customer screen `/t/$token`

One screen, five states from `TrackingView.state`. Each state has one big fact and at most one action. The
customer only reads; nothing on this page changes the order.

| State | Big fact | Under it | Action |
|---|---|---|---|
| `waiting` | `3rd` (position) | "of 7 today · 2 ahead of you"; Meter showing position/total; "Most likely **10:40**" + window "between 10:20 and 11:00"; "You booked a **window**, 08:00–12:00" or "an **exact time**, 10:30"; ETA basis line | none |
| `your_turn` | `12 min` (live ETA) | "Sipho is on the way · 4.2 km away"; "updated 30 s ago" | Call (tel: link to `contact.phone`) |
| `on_site` | "Sipho has arrived" | the service | none |
| `done` | "Done" | completion time | none |
| `unable` / `cancelled` | "Not today" | `message` (the reason) in an `alert`, contact | Call |

Under every state: a Timeline (UI SDK) of the order's steps (Booked → On the way → Arrived → Done) and a muted
contact row. When the live view moves them up, a `toast` says so ("You're now 2nd").

### 7.4 Technician screens

`/tech/$token`: the day.
- Header: date, `5 left · 2 done` in bold.
- List of `item` rows in queue order: position number (bold), customer name, street, time or window, status
  dot. The active task is first among the unfinished and highlighted with the muted surface. Done tasks are
  dimmed and listed last.
- A row with a status of `scheduled` can be swiped or tapped to open the task.
- `empty` state: "Nothing booked today."

`/tech/$token/$orderId`: the task.
- Name (bold, large), address + instructions, `notes`, service, time/window.
- Buttons: **Directions** (opens `directionsUrl`), **Call**, **Message** (`sms:`).
- Bottom action bar from `allowedActions`: one primary button for the next step (**Start**, **Arrived**,
  **Done**) and a secondary **Can't complete** that opens a `sheet` with a `textarea` for the reason
  (required).
- While a task is `en_route`, the page calls `navigator.geolocation.watchPosition` and posts to
  `/v1/tech/{token}/location` at most every 30 s. Ask for permission at the moment of **Start**, with a sentence
  that says why ("so Thandi can see how far away you are"). If it is denied, ETA falls back to `queue`.

## 9. Build order (each phase ends green: `bun test` + `bun run typecheck` + `bun run lint`)

**Phase 1: domain** (`packages/domain`, no I/O)
- identity normalisation, ids/tokens, order state machine, `DayQueue` (insert,
  move-to-front on out-of-turn start, remove, place), ETA strategies, haversine, directions URL.
- Tests: table-driven, including every invalid transition and a 10-order day with reschedules and cancels.

**Phase 2: persistence + Create Order**
- schema + migrations, repositories, `OrderService.create` (upserts, queue insert, rank rewrite, tracking token,
  events), API key script, `h()` wrapper, problem+json, `POST/GET /v1/orders`, `GET /v1/orders/{id}`,
  idempotency.
- Tests: create returns `orderId`, `trackingUrl` and queue place; `technicianUrl` only for a new technician;
  same technician by phone and by email resolves to one technician; idempotent retry returns the same `orderId`;
  422s mirror the OpenAPI constraints; nothing is sent anywhere.

**Phase 3: event bus, tracking API**
- EventBus, event log subscriber, `GET /v1/track/{token}`, SSE hub + `/stream`, `GET /v1/orders/{id}/events`.
- Tests: the tracking view never contains another customer's name, email, phone or address.

**Phase 4: technician API**
- Technician token issue (returned, not sent), `/day`, `/orders/{id}`, action Commands, location, technician SSE,
  PATCH (reschedule/reassign) and cancel with re-queue and the reason as the tracking page `message`.
- Tests: full day walk-through; one active order at a time; out-of-turn start moves to front; `unable` needs a
  note; reassign moves the order between two technicians' queues and both see it live.

**Phase 5: web**
- Setup (7.1), tokens (7.2), customer screen (7.3), technician screens (7.4), live updates.
- Seed script `bun run seed` creates a technician with 6 orders today and prints the technician link and each
  tracking link.

**Phase 6: end-to-end + handoff**
- One Bun test that boots the server on a random port and runs the README flow through HTTP + SSE:
  create 3 orders → customer 3 sees `3rd of 3 · 2 ahead` → technician starts customer 1 → customer 1 gets
  `your_turn` with distance after a location ping → arrive, complete → customer 2 sees `0 ahead` live and
  customer 3 sees `1 ahead` → integrator cancels customer 2 with a reason → customer 2 sees the reason and
  customer 3 sees `0 ahead`.
- `README` section "Run it" (`bun install`, `bun run key:create`, `bun run seed`, `bun run dev`).
- Move anything not done to FOUNDATION.md's roadmap.

## 10. Code rules

- DRY: one zod schema per OpenAPI schema, used by the API for parsing and by the web for types. One mapper per
  view (`toOrder`, `toTrackingView`, `toTechnicianDay`, `toTask`). One `h()` wrapper.
- Small files, one reason to change each. No file over ~200 lines; no function over ~40.
- No `any`. `strict: true`, `noUncheckedIndexedAccess: true`.
- Errors are values in the domain (`DomainError`), thrown only at the HTTP edge.
- Time comes from an injected `Clock` so tests can fix "now". Randomness from an injected `Random`.
- No comments that restate code. A comment explains a rule from this plan or the README.
- Biome for lint + format.
- Do not add features not in this plan. Put ideas in the roadmap instead.

## 11. Open questions (defaults in bold; build with the default, the owner can change it)

- **Q1 Email / SMS**: **out of the MVP**; the integrator sends the links. When it comes back, it is one
  subscriber on the event bus plus channel adapters, and the provider for South Africa still has to be picked.
- **Q2 Who is the "reachable support" contact on the customer page**: **the technician's phone** while
  `your_turn`/`on_site`, otherwise the integrator's support contact (a field on the API key: `support_phone`,
  `support_email`).
- **Q3 Hosting**: not decided. The app is one Bun process + one SQLite file, so any VM with a disk works.

## 12. Roadmap (moved out of the MVP)

- **Bump yourself up**: a customer pays to move to the front of the technician's remaining queue. SD stays order
  management only, so payment happens outside SD. The likely shape: the integrator takes the payment and then
  calls a `POST /v1/orders/{orderId}/priority` endpoint; `DayQueue` gets a `.prioritise(id)` that never displaces
  an active order. Still to decide: the order between two prioritised customers, and what happens when payment
  lands after the technician has started.
- Email / SMS notifications (Q1), manager view and rescheduling UI, provider/ISP overview, creating orders from
  chat, voice notes, outgoing webhooks.
